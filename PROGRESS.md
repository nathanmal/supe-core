# Progress Log — supe-core

Compressed history for Claude (and future-you) to reference across sessions. Entries are dated, newest first, terse — this is a state snapshot, not a changelog; `git log` is authoritative for that once this is under version control. Update whenever a session makes a meaningful change here, and prune/collapse old entries once they're no longer load-bearing context.

**Status:** Stable. Full Unit test coverage of the boot-order-critical pieces; Feature tests scaffolded but not yet run against a live DB.

- **2026-09-06** — Added `Admin\DashboardPage`: a shared top-level "Supe" admin menu (slug `supe`), registered by `Core` itself in its constructor (via `$adminMenuRegistry->addPage()`) before any module boots, so every module's own page can attach under it as a submenu by returning `DashboardPage::slug()` from `parentSlug()` instead of scattering into Settings/Media/etc. `render()` lists currently-loaded modules via `Core::getInstance()->getRegistry()->getLoadedModules()`. Updated the four sibling packages' pages (`supe-blocks`, `supe-email`, `supe-media`, `supe-security`) to nest under it instead of `options-general.php`. 3 new Unit tests (`DashboardPageTest`) plus a `CoreTest` assertion that the page is registered on construction; README's "Building an Admin Page" section and `stubs/ExampleAdminPage.php` updated to demonstrate attaching to the shared menu.
- **2026-09-06** — Added a shared admin menu/page system: `Contracts\AdminPageInterface`, `Support\AbstractAdminPage` (defaults for everything but `slug()`/`pageTitle()`/`render()`, plus a `view()` template helper), `Admin\AdminMenuRegistry` (collects pages, adds them to WordPress on `admin_menu`, top-level before submenu), and `Exceptions\InvalidAdminPageException`. `Core` now owns one `AdminMenuRegistry` instance (mirrors how it owns `ModuleRegistry`) and binds it into the container so `AbstractModule::addAdminPage()` can reach it. Deliberately placed in `supe-core` rather than a new sibling package — user's explicit call after being shown the tradeoff (ROADMAP.md's "stay minimal" note vs. every module needing one shared registry instance, which a separate optional package can't guarantee). 8 new Unit tests (`AdminMenuRegistryTest`, `AbstractAdminPageTest`); `stubs/ExampleAdminPage.php` added and wired into `stubs/ExampleModule.php`'s `boot()`; README's "Building a Module" section gained a "Building an Admin Page" sibling and two new hook rows (`supe/admin_page_registered`, `supe/admin_page_added`).
- **2026-09-05** — Extracted from the `supe` plugin as its own Composer package (`nathanmal/supe-core`, type `library`). Contains `Core` (formerly `Loader` — renamed per request), `Registry\ModuleRegistry`/`ModuleCandidate`, `Support\Container`/`AbstractModule`, `Contracts\ModuleInterface`, `Exceptions\*`, the global `supe()` helper (now in `src/functions.php`, autoloaded via Composer `files`), and `stubs/ExampleModule.php`. Namespace stayed `Nathanmal\Supe\*` at first — only the package/repo split, not the API (see the later namespace-remap entry below).
- **2026-09-05** — Remapped the package namespace from `Nathanmal\Supe\*` to `Supe\Core\*` (e.g. `Supe\Core\Core`, `Supe\Core\Registry\ModuleRegistry`), so the namespace root matches the package name (`nathanmal/supe-core`) the same way every module's does (`Supe\Blocks\*` for `nathanmal/supe-blocks`, etc.). Updated across every dependent package (`module-bootstrap.php`, `src/Supe{Name}.php`, `tests/bootstrap-feature.php`, Feature boot tests) and `composer.json`'s `psr-4`/`autoload-dev` maps. All 29 Unit tests re-verified passing after the remap.
- **2026-09-05** — Updated `README.md`'s "Building a Module" scaffold and `stubs/ExampleModule.php` to reflect the ecosystem's current conventions: `bootstrap.php` (not `module-bootstrap.php`) as the Composer `"files"` entry point, and every in-namespace module naming its main class `Module` (third-party example classes outside `Supe\*` can still use any name, as `ExampleModule.php`'s `GalleryModule` does). Also added the previously-missing `function_exists('add_action')` guard to both the README scaffold and `ExampleModule.php`'s docblock example, matching the real pattern used by every actual module.
- **2026-09-05** — **Bug fix:** `Exceptions/SupeException.php` bundled `SupeException`, `InvalidModuleException`, and `ContainerException` in one file. PSR-4 only autoloads a class from a file matching its own name, so `InvalidModuleException`/`ContainerException` silently failed to autoload whenever an actual error path ran (dormant bug — never hit on a normal successful boot). Split into three files matching their class names. (See `../supe/CLAUDE.md`'s "PSR-4 and Autoload Discipline" section — the same pattern recurred in `supe-email` and `supe-security`.)
- **2026-09-05** — Added the full Unit/Feature PHPUnit scaffold (`brain/monkey` + `yoast/wp-test-utils` + `wp-phpunit`). 12 Unit tests passing (`ContainerTest`, `ModuleRegistryTest`, `CoreTest`). `tests/Feature/CoreBootTest.php` written but not yet run against a real DB.
